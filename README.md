# AWD

Версия проекта: **0.2.0** (см. [CHANGELOG.md](CHANGELOG.md)).

## Архитектурное решение

### Основа решения

Для проекта AWD принимается **слоистая архитектура**. Подход основан на описании технологической платформы и Yii-приложения в статье «Слоистая архитектура на основе фреймворка yii» [1], а структура прикладных компонентов дополнительно сопоставляется с официальной моделью Yii 2 [2] [3].

> Слоистая архитектура — это такая архитектура системы, при которой система состоит из упорядоченной совокупности программных подсистем, называемых слоями, такой, что:
>
> 1. на каждом слое ничего не известно о свойствах и даже существовании последующих, более высоких слоёв;
> 2. каждый слой взаимодействует с непосредственно предшествующим, более низким слоем через заранее определённый интерфейс, не зная внутреннего устройства нижележащих слоёв;
> 3. каждый слой располагает ресурсами, которые он либо скрывает от других слоёв, либо предоставляет непосредственно следующему слою через абстракции.
>
> Практическое следствие для AWD: зависимости направлены сверху вниз, а детали реализации скрыты за контрактами и публичными API модулей.

В классической схеме статьи технологическая платформа разделяется на **Core layer**, **Shared layer** и **Application layer**. Для AWD сохраняется эта модель. Docker, nginx, PHP-FPM и PostgreSQL рассматриваются как среда исполнения и инфраструктурная граница, а не как повод нарушать логические границы прикладных слоёв.

### Слои AWD

| Слой | Назначение | Что находится в слое | Что слой не должен знать |
|---|---|---|---|
| **Core** | Низкоуровневые, стабильные и переиспользуемые технические абстракции | Yii 2, Composer-зависимости, базовые контракты, DTO/результаты, технические исключения, общие утилиты и абстракции доступа к инфраструктуре | Конкретные сценарии AWD, канал TRVL, конкретные источники и пользовательские процессы |
| **Shared** | Переиспользуемая бизнес-функциональность и интеграционные модули | Модули сущностей, профилей, источников, публикаций, стилей, медиа, тегов, актуальности и Telegram; публичные сервисы, репозитории и адаптеры модулей | Конкретные контроллеры и представления приложения, конкретную конфигурацию одного приложения и детали других Shared-модулей |
| **Application** | Сценарии конкретного продукта AWD и его пользовательские интерфейсы | Тонкие web-контроллеры, console-команды, конфигурация, сборка use-case сценариев, приложение TRVL, dashboard и специфические представления | Внутреннее устройство Shared-модулей, SQL, HTTP-клиенты, Telegram API и конкретные способы хранения данных |

Направление зависимостей для бизнес-кода: **Application → Shared → Core**. Core не зависит от Shared и Application. Shared не импортирует классы Application. Application обращается к Shared только через его публичные контракты, сервисы, команды, DTO и результаты. Прямой обход слоя, например вызов SQL из контроллера или обращение Application к внутреннему классу Shared-модуля, запрещён.

Инфраструктурные детали подключаются на границе системы. PostgreSQL, HTTP-источники, Telegram, файловое хранилище, нейронные сервисы и средства обработки изображений должны быть скрыты за интерфейсами и адаптерами. Конкретные реализации связываются с интерфейсами конфигурацией Yii и контейнером приложения. Поэтому замена PostgreSQL, API-адаптера или реализации генерации текста не должна требовать изменения use-case кода.

### Правила слоёв

Каждый слой обязан предоставлять следующему слою только необходимую абстракцию. Внутренние модели, SQL-запросы, структуру таблиц, HTTP-ответы, токены, файловые пути и SDK-объекты не должны утекать через публичный API модуля.

Связь между слоями выполняется через параметры, команды, DTO, типизированные результаты и исключения. Использование общих глобальных массивов, глобальных переменных и неявного состояния для обмена данными между слоями запрещено. Сервисы должны получать зависимости явно через конструктор или через конфигурацию композиционного корня.

`Yii::$app` и другие service locator-механизмы допускаются в entry points, конфигурации и composition root, где собираются зависимости приложения. В бизнес-коде предпочтительны явные зависимости и интерфейсы; бизнес-сервис не должен самостоятельно искать глобальный компонент, открывать соединение с БД или создавать внешний SDK-клиент.

### Application layer: тонкие контроллеры и команды

Web-контроллеры и console-команды являются точками входа. Они принимают и минимально валидируют входные данные, преобразуют их в команду или DTO, вызывают use-case сервис и формируют HTTP-, console- или JSON-ответ.

Контроллеры и команды не должны содержать правила парсинга, планирования публикаций, выбора стиля, преобразования изображений, работы с Telegram, SQL-запросов или сложных ветвлений предметной области. Такая логика располагается в Shared-модулях и вызывается через их публичное API.

Application layer отвечает за композицию конкретного продукта. Например, сценарий «поставить текст в очередь, обработать стиль и отправить на публикацию» может быть собран в Application-сервисе из публичных операций модулей очереди, стиля и публикации, но внутреннее устройство этих модулей ему неизвестно.

### Shared layer: функциональные модули

Функциональность, которая может быть использована более чем одним сценарием или приложением, оформляется как модуль с чёткой границей. На первом этапе модуль может находиться внутри Application, но при появлении второго потребителя его необходимо выделить в Shared без изменения публичного API.

В перспективе AWD должны быть выделены следующие функциональные области:

| Модуль | Ответственность |
|---|---|
| **Source/Entity** | Источники, сущности, посты, идентификация элементов и фиксация изменений |
| **Profile** | Профили, описания и слоганы |
| **Parsing** | Получение и нормализация данных из источников; повторный проход и обнаружение обновлений |
| **Publication** | Посты, порядок публикации, отложенная публикация и очереди |
| **Style** | Хранение образцов текста, структуры и выбранных стилей |
| **Media** | Изображения, преобразования и будущий логотип-вотермарк |
| **Tagging/Actuality** | Теги и примечания с датой актуальности информации |
| **Telegram** | Интеграция с каналом TRVL и будущим Telegram-ботом |
| **Dashboard** | Только если интерфейс нельзя оставить в Application; бизнес-операции остаются в Shared |

Каждый модуль должен скрывать свои модели хранения и инфраструктурные детали. Другие модули обращаются к нему через сервисы, интерфейсы, команды и DTO. Например, модуль Publication не должен требовать от вызывающего кода знания таблиц PostgreSQL, а модуль Style не должен заставлять контроллер работать с конкретной реализацией AI-провайдера.

В Yii 2 модуль является самодостаточной единицей, которая может включать `Module.php`, модели, контроллеры, представления, конфигурацию и консольные команды [3]. Для AWD это используется как организационный механизм, но границы слоёв важнее одной только структуры каталогов: наличие каталога `models` не делает любой код внутри него бизнес-логикой автоматически.

### Предлагаемая организация каталогов

Текущий Yii Basic Application остаётся рабочей точкой входа. По мере развития проекта структура должна эволюционировать в сторону явного разделения приложения и переиспользуемых модулей:

```text
AWD/
├── app/                         # Application layer и Yii entry points
│   ├── commands/                # тонкие console-команды
│   ├── controllers/             # тонкие web-контроллеры
│   ├── modules/                 # специфичные для приложения модули
│   ├── views/                   # представления приложения
│   ├── config/                  # конфигурация и composition root
│   ├── web/                     # публичный document root
│   ├── tests/                   # тесты приложения и сценариев
│   └── yii                      # console entry script
├── shared/                      # Shared layer, добавляется при выделении модулей
│   ├── modules/
│   ├── contracts/
│   └── config/
├── core/                        # Core layer проекта, если собственных абстракций станет достаточно
│   ├── contracts/
│   ├── dto/
│   ├── exceptions/
│   └── support/
├── docker/                      # среда исполнения, вне бизнес-слоёв
├── config/                      # конфигурационные шаблоны проекта
├── docker-compose.yml
└── README.md
```

Пока отдельные `core/` и `shared/` ещё не выделены в коде, это не является основанием для размещения бизнес-логики в контроллерах. Новая функциональность должна сразу проектироваться как кандидат на отдельный модуль с публичным API и возможностью последующего перемещения из `app/modules` в `shared/modules`.

### Конфигурация и подмена реализаций

Конфигурация Yii используется как слой связывания зависимостей и как средство уменьшения связанности. Компонент получает стабильный идентификатор или интерфейс, а конкретный класс выбирается в configuration/composition root. Замена локального адаптера на REST-клиент, одного хранилища на другое или одного AI-провайдера на другой не должна требовать изменений в контроллерах и use-case сценариях.

Конфигурация окружения, секреты и параметры подключения не должны зашиваться в исходный код. Локальные значения передаются через `.env` и Compose, а код получает их через конфигурационный слой. Секреты не коммитятся и не выводятся в логи.

### Модель данных и PostgreSQL

PostgreSQL является инфраструктурой хранения. Таблицы, индексы, SQL и ORM/ActiveRecord-модели относятся к нижнему уровню модуля и не должны становиться контрактом для Application layer. Use-case сервисы работают с репозиториями или доменными API, а не с прямыми SQL-запросами.

Схема данных должна поддерживать идентификацию источника и внешнего элемента, дату последнего наблюдения, версию или хэш содержимого, состояние обработки и дату актуальности. Это позволит реализовать повторный полный проход диапазона без дублирования, обнаружение изменений и добавление новых элементов. Конкретные таблицы и поля будут проектироваться отдельным этапом, когда начнётся реализация парсинга.

### Тестируемость и развитие

Каждый Shared-модуль должен иметь тесты публичного API и основных бизнес-правил. Инфраструктурные адаптеры тестируются отдельно от use-case сценариев. Application-тесты проверяют сборку сценариев и точки входа, но не должны дублировать внутренние тесты Shared-модулей.

В дальнейшем система сборки, миграций, CI, Selenium, очереди и фоновые процессы добавляются как инфраструктура вокруг слоёв, не разрушая их границы. Новая технология не должна становиться причиной прямой зависимости контроллеров от внешнего SDK или хранилища.

### Архитектурные критерии при code review

Перед добавлением функциональности необходимо ответить, к какому слою и модулю она относится, какой публичный контракт предоставляет и какой нижний слой использует. Следует проверить, не знает ли нижний слой о верхнем, не протекают ли наружу детали хранения или SDK, не появилась ли бизнес-логика в контроллере и можно ли заменить инфраструктурную реализацию через конфигурацию.

Функциональный блок считается корректно выделенным, если его можно вызвать из другого Application-сценария через публичный API, протестировать без реального внешнего сервиса и при необходимости перенести между приложениями без переписывания внутренней логики. Это поддерживает ключевые цели подхода из статьи: повторное использование, расширяемость, единый деплой и возможность менять детали реализации без изменения верхних слоёв [1].

### Модель данных

Публикации канала TRVL хранятся в четырёх таблицах PostgreSQL:

| Таблица | Назначение |
|---|---|
| `publications_post` | Посты канала: запланированные (`published_at` в будущем, `telegram_id` пуст) и уже опубликованные (`telegram_id` заполнен) |
| `publications_draft` | Черновики — записи до отправки в Telegram |
| `publications_edited` | Архив редактирования опубликованных постов (те же поля, что у поста, плюс `edited_at`); пустой `edited_at` означает, что сообщение в канале ещё не заменено новым текстом |
| `publications_deleted` | Архив удалённых постов — soft-delete (те же поля, что у поста, плюс `deleted_at`); пустой `deleted_at` означает, что сообщение ещё не удалено из канала |

Данные форума (см. [PARSER.md](PARSER.md)): `topic` — топики, `post` — посты топиков, `member` — профили участников (авторы топиков и постов).

### Открытие на редактирование

При нажатии на кнопку-иконку редактирования (или двойном клике по элементу списка) публикация любого типа — черновик, запланированная, опубликованная или удалённая — открывается на редактирование в форме «Новая публикация»: текст подставляется в поле ввода, дата публикации (для постов и удалённых записей с непустым `published_at`) — в поле даты, а тип и id исходной записи передаются скрытыми полями `publicationSource` / `publicationSourceId`.

### Сценарии сохранения

Дальнейшее поведение зависит от типа редактируемой записи и нажатой кнопки — «Опубликовать» или «Сохранить». Восемь сценариев (логика в `PublicationsService::saveFromForm`, `app/shared/Publications/Service/PublicationsService.php`):

| Редактируемая запись | Кнопка | Что происходит |
|---|---|---|
| Запланированная публикация | **Опубликовать** | Штатное обновление в таблице публикаций: `published_at` обновляется текущим значением соответствующего поля формы, `updated_at` — временем изменения, `created_at` сохраняется в неизменном виде |
| Запланированная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Опубликованная публикация | **Опубликовать** | Запись удаляется из таблицы публикаций и добавляется в `publications_edited`: копируются значения всех полей, `updated_at` — текущее время, `edited_at` остаётся пустым |
| Опубликованная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Черновик | **Опубликовать** | Запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `updated_at` — текущее время, `created_at` сохраняется в неизменном виде |
| Черновик | **Сохранить** | Штатное обновление в таблице черновиков; `updated_at` — время изменения, `created_at` сохраняется в неизменном виде |
| Удалённая запись | **Опубликовать** | Запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из поля формы; `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |
| Удалённая запись | **Сохранить** | Запись удаляется из `publications_deleted` и добавляется в таблицу черновиков; `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |

Отдельно от формы работают кнопки-иконки на элементах списков:

- **«Опубликовать» на черновике** — запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `created_at` без изменений, `updated_at` и `published_at` — текущее время (пост сразу готов к отправке в канал периодической задачей)
- **«Опубликовать» на запланированной публикации** — запись перестаёт быть запланированной: `published_at` и `updated_at` становятся равными текущему времени, `created_at` не меняется
- **«Переместить в черновик» на публикации** (пост любого типа — запланированный или опубликованный) — запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `created_at` не меняется, `updated_at` — текущая дата и время
- **«Удалить» на публикации или черновике** — запись перемещается в `publications_deleted`: `created_at` и `published_at` сохраняют свои значения (у черновика `published_at` остаётся пустым), `updated_at` заполняется текущим временем, `deleted_at` не заполняется. Периодическая задача `telegram/delete-due` затем удаляет сообщение из канала по `telegram_id` (у записей без `telegram_id` — черновиков и запланированных постов — сообщения в канале не было, им `deleted_at` проставляется сразу) и записывает в `deleted_at` время удаления

Общие правила всех сценариев:

- `created_at` исходной записи всегда сохраняется неизменным;
- `updated_at` всегда устанавливается в текущее время — момент обновления или перемещения между таблицами;
- отправка в Telegram из формы не выполняется: записи уходят в канал только периодической задачей `publishDue()` по наступлении `published_at`.

Для новой записи (форма открыта без редактирования) кнопка «Опубликовать» создаёт запланированный пост, кнопка «Сохранить» — новый черновик.

### Блок «Удаленные»

Блок «Удаленные» на странице публикаций выводит записи из `publications_deleted` по убыванию `updated_at` (самые свежие сверху). Бейдж статуса отражает фазу удаления: **«Удалено»** — сообщение ещё в канале (`deleted_at` пуст, его ждёт задача `telegram/delete-due`), **«Удалено из канала»** — сообщение уже удалено (`deleted_at` заполнен).

У элементов блока три кнопки-иконки, восстанавливающие запись без открытия формы (логика в `PublicationsService`):

- **«Опубликовать»** (`publishDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций: `created_at` сохраняется, `published_at` и `updated_at` — текущее время, старый `telegram_id` сбрасывается (новое сообщение получит свой id после отправки в канал). Ожидающееся удаление из канала отменяется вместе с архивной строкой
- **«Запланировать публикацию»** (`scheduleDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из модального окна: `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; задача `publishDue()` отправит пост в канал по наступлении `published_at`
- **«Перенести в черновик»** (`moveDeletedToDraft`) — запись удаляется из `publications_deleted` и добавляется в таблицу черновиков: `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается

Редактирование удалённой записи (карандаш или двойной клик) открывает форму «Новая публикация» с источником `deleted` и добавляет два сценария к таблице выше: кнопка **«Опубликовать»** восстанавливает запись как запланированный пост с датой из поля формы, кнопка **«Сохранить»** — как черновик; в обоих случаях архивная строка `publications_deleted` удаляется, а ожидающееся удаление из канала отменяется.

### Блок «Форум»

Страница публикаций разбита на два ряда: сверху на всю ширину идут блоки «Фильтры» и «Форум», ниже — два блока на половину ширины (`col-sm-6`), слева превью публикации, справа форма «Новая публикация». Разделение нужно затем, чтобы рост превью не сдвигал форму.

Поле ввода текста формы подстраивает высоту под содержимое (не больше 80% видимой области), но не при каждом нажатии клавиши, а через 5 секунд после последнего изменения: измерение высоты требует `height: auto`, на время которого поле схлопывается до двух строк и утаскивает за собой прокрутку страницы.

Блок «Форум» выводит 10 самых свежих топиков форума AWD (таблица `topic`, только `login_required = FALSE`) по убыванию `published_at`; к каждому топику — 10 самых свежих постов (таблица `post`, связь по `topic_id`) по убыванию `posted_at` (выборка `ForumRepository::latestTopicsWithPosts(10, 10)`).

У топика выводятся полностью, без обрезок: `source_url` (кликабельная ссылка), `title`, `published_at`, `content_text` (полный текст), `content_html` (полный HTML-исходник в свёрнутом блоке `<details>` — экранирован, поскольку исходный HTML форума содержит рекламные скрипты), `image_urls` (все изображения кликабельны). У постов: `number`, `title`, `published_at` (`posted_at`), `content_html`, `content_text` и `source_url` — тоже полностью. Имена и аватары авторов подтягиваются из таблицы `member` (при отсутствии аватара — иконка-заглушка).

Посты не выводятся, пока парсер их не сохранил: у недавно появившихся топиков постов ещё может не быть, тогда у топика отображается счётчик «0».

#### Статусы топиков и постов

Топик и пост помечаются строкой в таблицах `publications_topic_map` / `publications_post_map`: `telegram_id IS NULL` — элемент отмечен кнопкой «Просмотрено» (`ForumRepository::markTopicViewed` / `markPostViewed`), заполненный `telegram_id` — опубликован в канале. В блоке «Форум» это бейдж «Просмотрено» или «Опубликовано» с дополнением `TG: <telegram_id>`; элемент без строки в таблице-маппинге считается непросмотренным и неопубликованным.

#### Фильтры блока «Форум»

Блок «Фильтры» над «Форумом» содержит два переключателя и слайдер: «С изображениями» (`withImages`), «С привязанными постами» (`withPosts`) и «Кол-во изображений» (`imagesCount`, `0` — без ограничения). Фильтры влияют только на выборку «Форума» (топики и их посты), списки публикаций, черновиков и удалённых записей не затрагивают; состояние хранится в нормализованном виде (`SiteController::normalizeForumFilters`).

- «С изображениями» оставляет топики, у которых есть свои изображения или хотя бы один пост с изображениями; списки постов сжимаются до постов с изображениями
- «Кол-во изображений» оставляет топики ровно с `imagesCount` изображений, а среди постов — посты ровно с `imagesCount` изображений
- «С привязанными постами» — правила ниже

Синхронизация фильтра с сессией и URL: состояние живёт в сессии (`forumFilters`) и является единственным источником истины, адресная строка — его зеркало.

- Любое изменение фильтра (переключение тумблера, отпускание слайдера) уходит на `site/forum-filter-save`, сохраняется в сессию и перезапрашивает блоки по ajax
- Ответ сервера содержит `url` — адрес, соответствующий сохранённому состоянию (`SiteController::forumFilterUrl`), и отрендеренный блок «Форум»; JS подставляет адрес в строку браузера через `history.replaceState` и подменяет содержимое блока, целиком страницу не перезагружает
- При открытии страницы активный фильтр сессии приоритетен над GET-параметрами: перезагрузка или переход по ссылке не «включают» фильтр обратно. Если в сессии активного фильтра нет, она принимает параметры запроса. Когда URL не совпадает с состоянием сессии, `actionPublications` отвечает 302 на адрес из `forumFilterUrl()`; сравнение идёт по нормализованным значениям, поэтому цикл редиректов невозможен
- Сессию очищает только кнопка «Очистить» в блоке фильтров (`site/forum-filter-clear`)

Правила фильтра «С привязанными постами» (`ForumRepository::latestTopicsWithPosts` при `$withPostsOnly = true`):

1. у топика нет привязанных постов в таблице `post` — топик не показывается
2. топик непросмотрен и неопубликован — показываются все его привязанные посты, независимо от того, просмотрены или опубликованы они
3. топик просмотрен или опубликован, но среди его постов есть хотя бы один непросмотренный и неопубликованный — показываются все посты топика
4. топик не показывается, если и он сам, и все его привязанные посты просмотрены или опубликованы

Обработанные посты из правил 2 и 3 приходят в выборку со своими статусами, поэтому у них выводятся бейджи «Просмотрено»/«Опубликовано» и `TG: <telegram_id>`. Лимит «10 самых свежих постов» сохраняется и при активном фильтре.

### Сортировка списков

Блок «Публикации» выводит записи по убыванию `published_at`, блок «Черновики» — по убыванию `updated_at`, блок «Удаленные» — по убыванию `updated_at` (самые свежие сверху).

## Публикации в канал

Подробная документация по функциональности публикаций и интеграции с Telegram каналом вынесена в отдельный файл [PUBLICATIONS.md](PUBLICATIONS.md).

Краткий обзор:

- Публикации хранятся в четырёх таблицах: `publications_post` (основные посты), `publications_draft` (черновики), `publications_edited` (история редактирования), `publications_deleted` (soft-delete архив)
- Отправка в Telegram выполняется исключительно через периодические задачи (`telegram/publish-due`, `telegram/delete-due`, `telegram/edit-due`), а не напрямую из формы
- Управление каналом Telegram (описание, посты, закрепление, удаление) реализовано в `ChannelService`
- Консольные команды доступны через `TelegramController` (`php yii telegram/*`)
- Конфигурация требует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHANNEL_ID` в `.env`

Для полной информации см. [PUBLICATIONS.md](PUBLICATIONS.md).

## Релизы

Релизы публикуются автоматически на [GitHub Releases](https://github.com/Resident234/awd/releases) через GitHub Actions (`.github/workflows/release.yml`).

Порядок выпуска релиза:

1. Добавить в `CHANGELOG.md` секцию `## [X.Y.Z] - ГГГГ-ММ-ДД` (формат Keep a Changelog)
2. Закоммитить и запушить изменения в `master`
3. Создать и запушить тег:

```
git tag vX.Y.Z
git push origin vX.Y.Z
```

Workflow срабатывает на пуш тега `v*`: извлекает секцию соответствующей версии из `CHANGELOG.md` (префикс `v` срезается автоматически) и создаёт релиз с именем тега и телом из заметок CHANGELOG. Если такой релиз уже существует, его тело не перезаписывается — при необходимости обновить заметки пересоздайте релиз или отредактируйте его вручную.
